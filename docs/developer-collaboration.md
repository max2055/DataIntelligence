# 双人开发分工与前置准备

本文面向两位均使用 AI Coding 工具的开发者，讨论如何以公司的固收业务为切口，从现有 demo 推进到可验证的智能问数试点。本文中的分工、接口状态和阶段安排是建设建议，并不表示这些能力已经实现。

现有实现与运行方式见[项目说明](../README.md)。更长期的能力边界见[与 Palantir Ontology 的对比](palantir-ontology-comparison.md)。

## 1. 分工原则与当前基础

建议按“理解用户要问什么”与“确保系统算得对”分工，并共同维护业务模型和验收样例。AI Coding 工具可以提高实现效率，但指标口径、接口和正确性标准仍需团队明确。

当前 demo 已实现以下链路：

> 规则模拟解析 → 结构化意图 → 模型校验与计划展开 → 参数化 SQL → MySQL 实际查询与结果解释。

自然语言解析尚未接入 LLM；查询编译器支持的是“单日组合、汇总分子 / 快照分母”这一类计算。下一步围绕真实业务问题、脱敏数据和业务确认的答案展开。

## 2. 两位开发者的研究与交付方向

| 方向 | 开发者 A：问题理解与交互 | 开发者 B：业务模型与查询执行 |
|---|---|---|
| 核心问题 | 用户到底想查什么？表达不完整时如何澄清？ | 指标应该如何计算？数据从哪里来？ |
| 研究重点 | LLM 意图解析、业务术语匹配、上下文理解、歧义处理 | 指标口径、数据粒度、关联规则、计划生成、SQL 正确性 |
| 在 demo 上继续做 | 替换 `parse_question()`，接入真实 LLM | 扩展 `ontology.json`、`build_plan()` 和执行层 |
| 主要产出 | 意图解析模块、澄清流程、问题测试集 | 可执行业务模型、数据映射、查询编译器、结果基准 |
| 验证标准 | 指标、日期、范围、条件是否理解正确 | 数值、名单、异常处理、权限是否正确 |

例如用户提问：“帮我看看最近信用债仓位比较高的产品。”

A 负责识别和处理三个待明确的地方：“最近”是哪天、“仓位”用什么分母、“比较高”是什么阈值。通过业务默认规则或追问，形成明确意图。

B 负责定义信用债包含哪些证券、使用哪个市值字段、净资产来自哪里、日期如何对齐，以及缺数据时如何处理。

### 共同维护的边界

业务模型由两人共同设计，建议由 B 负责主要实现和维护。A 使用其中的名称、别名、适用范围和口径帮助 LLM 理解，B 使用公式、粒度和映射生成计算。两端应消费同一份定义，避免产生不一致的指标解释。

除了两位开发者，还需要明确业务支持角色：固收业务人员确认指标和验收答案，熟悉原系统的数据人员协助解释表结构、字段和更新规则。这些角色可以由现有业务同事承担。

## 3. 先确定接口，再并行开发

以现有[结构化意图样例](../examples/intent.json)为第一版基础，共同约定：

- 对象、指标、范围采用哪些 ID。
- 日期、比例、比较符和返回字段采用什么格式。
- 缺少信息时采用哪些默认值，哪些情况必须澄清。
- 不支持的问题返回什么状态。
- 查询结果如何携带口径、日期、模型版本和异常说明。

建议语言理解模块可以返回三类结果。以下状态是待设计的接口建议，当前代码尚未实现状态封装：

| 状态 | 示例 | 下游动作 |
|---|---|---|
| 可以执行 | 指标、日期、范围和条件均已明确 | 进入模型校验和计划生成 |
| 需要澄清 | “占比”存在净资产和总资产两种口径 | 向用户提问，补齐信息后再次解析 |
| 暂不支持 | 用户询问尚未定义的收益率指标 | 解释当前支持范围 |

LLM 应参考已登记的业务定义输出意图，程序负责检查 ID、类型、必要条件和权限上下文。JSON 结构合法不代表业务口径选择正确；语义正确性仍需通过样例评估和澄清机制控制。

A 可以用模拟查询结果开发交互，B 可以直接使用固定意图 JSON 开发编译器。用户身份与可访问范围由执行端提供，不能允许用户意图覆盖。

## 4. 公司需要准备的前置材料

优先准备真实问题、确认过的口径和对应数据，再落实为数据库与测试环境。

| 材料 | 建议内容 | 用途 |
|---|---|---|
| 真实业务问题清单 | 先选 10～20 个高频问题，附不同问法 | 确定第一阶段范围，测试语言理解 |
| 指标口径说明 | 分子、分母、估值日、市值口径、分类体系、币种、异常规则 | 建立可执行模型 |
| 数据字典和表关系 | 表字段含义、主键、粒度、关联键、状态字段、更新频率 | 避免字段误用、重复关联和跨日期混算 |
| 开发数据 | 脱敏快照或模拟数据，包含正常和异常情况 | 在相同数据上复现和比较结果 |
| 业务确认的答案 | 给定日期下应返回的组合与数值 | 判断计算是否正确 |
| 用户与权限规则 | 用户可访问哪些组合，部门或产品范围如何划分 | 落实执行端的访问限制 |
| 运行环境 | 数据库版本、连接方式、只读账号、LLM 使用方式及数据边界 | 统一开发与联调环境 |

正确答案应尽量来自业务确认的报表或人工核算，并由开发者核对数据来源与口径。不能仅依靠 AI 生成 SQL，再用另一个 AI 判断它是否正确。

## 5. 固收数据库怎样准备

如果公司已有业务系统，可以先整理一组脱敏数据表或标准视图，作为项目稳定的数据入口。当前[数据库初始化脚本](../database/init.sql)中的四类数据可作为起点。

| 数据对象 | 至少需要的字段 | 必须确认的事项 |
|---|---|---|
| 组合主数据 | 组合 ID、名称、业务类型、管理部门或权限归属 | 跨系统 ID 能否对齐，是否存在母子组合 |
| 证券主数据及分类 | 证券 ID、名称、资产类别 | 信用债分类标准是什么，分类是否随时间变化 |
| 持仓快照 | 组合 ID、证券 ID、账户、估值日、市值 | 唯一粒度是什么，是否含应计利息，是否统一币种 |
| 组合估值快照 | 组合 ID、估值日、净资产、总资产、数据状态 | 是否有多版本估值，哪个版本可用于正式查询 |

表格描述的是业务试点需要核实和准备的数据；其中总资产等字段尚未包含在当前 demo 中。

真实持仓可能区分投资账簿、资产单元、批次等维度，不能直接假定 demo 的唯一键适用于公司数据。

当前 `holdings_complete` 是人为准备的完整性标志。真实环境应从估值批次完成状态、导入任务状态或对账结果获得依据，不能把所有记录简单标为完整。

分类字典、历史分类、汇率和权限映射等数据，可以根据第一批问题逐步加入。如果试点仅支持人民币、单日和固定分类，应明确说明这些限制。

### 开发和联调环境

两位开发者使用相同的数据结构和初始化脚本，每人运行独立的本地数据库，再准备一个共享联调环境。这样一人的数据修改不会影响另一人的测试。

当前 demo 初始化 SQL 仅在新数据卷上自动执行。已有数据库的结构变化，应通过明确的迁移方式管理；修改初始化文件不等于已有数据库已更新。

## 6. 用共同验收样例连接两人的工作

每个业务问题都准备一份固定材料。下面的 FI-001 使用现有 demo 的虚构数据。

| 项目 | 示例 |
|---|---|
| 问题编号 | FI-001 |
| 标准问题 | 2026-09-14，信用债占净资产超过 10% 的固收组合有哪些？ |
| 非标准问法 | “信用债仓位超过一成的固收产品帮我列一下” |
| 确认口径 | 信用债市值 / 同日组合净资产，严格大于 10% |
| 标准意图 | `credit_bond_nav_ratio`、`gt`、`0.1`，附日期与范围 |
| 数据快照 | 一个固定且可重建的测试数据版本 |
| 预期答案 | P001：12%；P004：25% |
| 边界场景 | 恰好 10%、没有信用债、净资产缺失、持仓不完整、无权限 |

非标准问法没有日期且存在分母歧义。验收时应明确它是否有上下文或已确认默认值；没有这些依据时，预期行为应是澄清，不能无条件套用标准问题的答案。

A 验证各种问法能否得到正确意图或正确触发澄清；B 验证标准意图能否得到正确结果。联调时再连接两段，比较最终名单、数值和说明。

| 现象 | 优先检查 |
|---|---|
| 指标 ID 选错 | 语言理解、别名与业务概念绑定 |
| 指标正确但数值错误 | 指标定义、字段映射、关联和计算实现 |
| 意图与程序正确，源数据错误 | 数据质量、批次和权威数据源 |

## 7. GitHub 与 AI Coding 协作方式

建议每个任务使用独立分支，通过 PR 合并，由另一位开发者审查。每个人和自己的 AI Coding 工具使用独立 checkout 或 worktree。

优先共同维护三类资产：

1. 接口约定：意图、澄清状态、结果和错误格式。
2. 业务模型：指标 ID、口径、别名、数据映射与版本。
3. 验收样例：用户问法、标准意图、固定数据与预期结果。

模型 ID 或接口变化应说明影响范围，并同步更新两端的样例和实现。涉及同一文件时，提前约定修改负责人，避免两套 AI 工具同时进行不兼容的重构。

给 AI Coding 工具布置任务时，把验收条件写进任务。例如，交给 A 的任务可以是：

> 支持将“超过一成”转换为 `gt` 和 `0.1`；分母有歧义时返回需要澄清；不能增加模型中不存在的指标 ID。

交给 B 的任务可以是：

> 支持按指定日期读取净资产；多账户持仓必须累加；恰好 10% 不命中；缺失净资产不得按零占比处理。

## 8. 第一轮共同完成的事项

1. 选定一小组真实固收问题，并列出暂不支持的范围。
2. 拿到对应脱敏数据，确认数据粒度、关联和更新规则。
3. 由业务确认指标口径与标准答案。
4. 冻结第一版意图接口和澄清规则。
5. A 与 B 分别推进语言理解和模型执行，再用同一批验收样例完成联调。

这轮完成的标准是：明确问题能得到可核对的答案，歧义问题能正确澄清，不支持的问题能明确返回原因。
