# 与 Palantir Ontology 的差距及演进建议

本文基于当前 DataIntelligence demo 和项目讨论，对照 Palantir 官方文档说明能力与目标差异。文中的固收场景是本项目的设计示例，阶段性能力是建设建议，并非当前已经实现。

当前实现见[项目说明](../README.md)，人员分工与数据准备见[双人开发分工与前置准备](developer-collaboration.md)。

## 1. 定位差异

本项目目前建设的是面向智能问数的业务语义模型和查询引擎。Palantir Ontology 面向企业业务对象、计算、决策和操作的统一运行体系。

两者已有共同基础：以业务对象、关系和规则连接底层数据。查询是 Palantir 本体体系的一种用途；其官方定义同时包含对象、属性和关系等语义元素，以及动作、函数和动态安全控制等操作元素。参见 [Ontology 官方概述](https://www.palantir.com/docs/foundry/ontology/overview/)。

需要区分两种差距：一种是 demo 尚未实现的工程能力；另一种是即使智能问数完善后，与完整企业运营体系仍然存在的目标差异。Palantir 的这些能力也需要配置和建设，平台不会自动解决企业内部的口径与数据质量问题。

## 2. 六类主要差距

| 维度 | 当前项目 | Palantir Ontology 的方向 | 固收业务中的例子 |
|---|---|---|---|
| 业务对象 | 对象主要用于组织字段和生成查询 | 对象实例具有身份、属性和关系，供不同应用访问和操作 | 同一个组合用于问数、风险监控、复核与处置 |
| 关系表达与使用 | 有限关联主要服务 SQL JOIN | 关系可被查询、遍历，并用于应用和业务逻辑 | 从发行人找到债券、持仓组合和负责人 |
| 业务计算 | 固定的“汇总分子 / 快照分母”结构 | 函数封装复杂且可复用的业务逻辑 | 敞口计算、压力情景与复杂风险指标 |
| 动作与业务闭环 | 查询后输出结果 | 动作修改对象与关系，执行验证并连接流程 | 超限后创建复核任务、分配责任人、记录结果 |
| 权限和治理 | 固定模拟身份、查询条件和模型版本标签 | 对数据、对象及操作实施治理与权限控制 | 投资经理与复核人员具有不同访问和操作权限 |
| 数据和应用支撑 | 单个 MySQL 数据源和命令行 demo | 基于平台数据集成能力，为多种分析和业务应用提供支撑 | 投研、交易、估值、风控共享一致业务概念 |

数据接入、处理及应用构建还涉及 Foundry 等平台配套能力，不能将它们全部归结为一份本体定义文件的能力。

## 3. 对象：从查询配置到可复用的业务身份

当前 `portfolio` 配置主要告诉程序：组合来自 `portfolios` 表，身份字段是 `portfolio_id`。它主要服务一次查询的生成。

Palantir 区分对象类型、对象实例和对象集合。在固收场景中可以对应为：

- 对象类型：投资组合。
- 对象实例：稳健固收一号。
- 对象集合：信用债占净资产比例超过 10% 的固收组合。

同一个组合对象可以被不同应用引用。查询组合、查看关联持仓、创建复核事项时，使用一致的业务身份与定义。参见[对象类型官方说明](https://www.palantir.com/docs/foundry/object-link-types/object-types-overview/)。

本项目需要逐步回答：投资系统、估值系统和风控系统中的记录，怎样确定对应同一个组合？这涉及跨系统 ID 映射、属性来源、权威数据源和更新规则。表字段映射仅完成其中一部分。

## 4. 关系：从特定 JOIN 到业务路径与计算语义

当前信用债占比问题主要使用“持仓 → 证券 → 证券分类”。如果问题变成：

> 某发行人信用评级下调，哪些组合受影响？各组合敞口是多少？谁负责管理？

需要遍历的业务路径可能是：

> 发行人 → 债券 → 持仓 → 组合 → 管理人。

当前程序尚未实现这类通用关系遍历及路径上的复杂计算。虽然模型声明了多个关系，当前证券关联主要读取 `holding_security`；组合与汇总结果的关联使用指标的 `join_key` 和粒度。它不是任意关系图上的通用计划引擎。

沿关系找到组合，与正确计算敞口是两项能力。计算还必须明确：

- 是否包含担保关系或关联主体。
- 使用哪一天的持仓和评级。
- 是否穿透基金或资管计划。
- 同一风险主体经过多条路径出现时如何避免重复计量。

这些规则需要业务建模。是否采用图数据库是实现选择，不能替代上述定义。

## 5. 计算：从固定计划到可组合的指标与函数

当前已实现的计划结构为：

> 筛选组合 → 汇总分子 → 读取分母 → 计算比率 → 判断阈值 → 返回结果。

它适合信用债占净资产比例及部分相似指标。仅增加 JSON 配置，还无法自动支持期间收益率、评级迁移后的风险变化、多层产品穿透或利率冲击情景计算。

Palantir Functions 支持开发者基于对象属性和关系编写复杂逻辑，并供不同应用调用。参见[函数官方说明](https://www.palantir.com/docs/foundry/functions/overview/)。

本项目可逐步采用两类计算能力：

| 方式 | 适合的计算 | 需要明确的约束 |
|---|---|---|
| 声明式指标 | 常见筛选、汇总、比率等 | 单位、粒度、来源、日期与异常规则 |
| 注册业务函数 | 收益率、穿透、压力情景等复杂算法 | 输入、输出、版本、权限、确定的实现与测试样例 |

复杂函数同样需要工程实现和验证。LLM 可以选择已登记能力和填入参数，业务公式不能由它在执行时随意创造。

## 6. 动作：从得到答案到完成业务闭环

当前链路止于“找到信用债占比超过 10% 的两个组合”。后续业务闭环可能包括：

1. 判断是否触发各组合适用的限额。
2. 创建复核事项。
3. 分配负责人。
4. 提交处理意见与审批。
5. 跟踪状态和处理结果。

“超过 10%”只是本例的查询条件，是否构成超限必须依据另外确认的业务规则。

Palantir Action Types 可以定义对象、属性与关系的修改，并配合参数、执行条件、权限检查和副作用；相同动作逻辑可在多个应用中复用。参见[动作官方说明](https://www.palantir.com/docs/foundry/action-types/overview/)。

若本项目增加“创建超限复核任务”，应明确输入哪些组合、谁能发起、必须满足什么条件、产生哪些记录。LLM 可辅助理解用户希望采取的动作，是否合法以及如何落地应由系统规则控制。

是否真正写回公司原业务系统，还需要单独设计集成接口、失败处理和一致性机制；修改本体对象不能自动等同于完成外部系统写回。

## 7. 治理：从标签和筛选到可追溯的运行规则

当前模型虽然包含 `version`、`owner` 和权限字段，但尚未形成完整治理流程。身份由程序固定注入，数据库只读账号可读取整个演示库，行范围由应用生成的查询限制。

长期使用需要明确以下问题：

- 信用债分类口径由谁提出、谁确认修改。
- 模型变更会影响哪些指标和应用。
- 历史报告是否继续使用旧口径。
- 一次结果使用了哪个模型版本和哪批数据。
- 同一个人是否有不同的查看、修改与执行动作权限。

对固收分析而言，结果可复现通常需要同时固定业务口径版本和数据版本。一个 JSON 版本号本身不提供版本审批、影响分析或数据快照能力。

## 8. 两人团队的阶段性演进建议

| 阶段 | 建设重点 | 验证方式 |
|---|---|---|
| 第一阶段：问数可信 | 真实业务口径、统一对象 ID、数据质量、身份权限、标准答案 | 明确问题得到正确结果；歧义正确澄清；异常数据和无权限数据按规则处理 |
| 第二阶段：能力复用 | 可复用指标和函数、更多关系路径、版本和结果追溯 | 新问题可组合已有定义；结果可定位到口径与数据来源 |
| 第三阶段：业务闭环 | 对象详情、复核任务、业务动作和状态流转 | 查询结果可以进入受控的业务流程，并留下处理记录 |

第一阶段以智能问数为目标是合理的。最值得持续借鉴的是：让对象、指标、权限和业务逻辑成为可复用的系统资产，而不必立即追求完整平台的功能规模。

一个具体的衡量标准是：新增风险监控页面或复核流程时，能否复用已有组合对象、指标口径、关系与权限，而无需重写一套业务定义。
